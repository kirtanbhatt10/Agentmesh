# Protocol Overview

> ⚠️ **Status:** Everything on this page is a **proposed** design. Schemas and contracts are drafts for discussion and are not finalized. The `agentmesh` package implements them as a reference (validators, agent server, registry and client — see [http-api.md](http-api.md)), so the drafts can be exercised end to end.

AgentMesh's protocol defines the common vocabulary that independent agents use to discover each other, delegate tasks, and report results. This page summarizes the core concepts. Draft JSON Schemas exist in [`specs/`](../specs/README.md) and are explicitly proposals, not finalized contracts.

## Agent identity

Every agent has a stable, unique identity within a mesh, tentatively composed of:

- **Agent name / ID** — a unique identifier (exact format: *proposed, not finalized*).
- **Version** — the agent's own version, useful when multiple deployments of the same agent exist.
- **Endpoint base URL** — where the agent's API lives.
- **Capabilities** — machine-readable descriptions of what the agent can do (see [agent-discovery.md](agent-discovery.md)).

## Manifests

A **manifest** is a self-description an agent serves (at `/manifest`). It declares identity, version, capabilities, and the endpoints a caller should use for delegation. Manifests make discovery possible without hard-coding knowledge of specific agents. The draft manifest schema is [`specs/manifest.schema.json`](../specs/manifest.schema.json); see [agent-discovery.md](agent-discovery.md).

## Task payloads

A **task** is the unit of delegation. The proposed payload keeps one unified JSON shape for requests and responses so agents can interoperate regardless of implementation language or model.

Proposed fields (*all drafts*):

| Field | Purpose |
| --- | --- |
| `task_id` | Unique identifier for this task, generated by the delegator or receiving agent (assignment strategy: *proposed, not finalized*; the reference implementation has the delegator assign it). |
| `conversation_id` | Correlates multiple tasks that belong to one logical workflow (e.g., a research task and a writing task serving the same user request). |
| `capability` | Which advertised capability the delegator is invoking. |
| `context` | Structured input the agent needs: instructions, documents, prior results, references. |
| `constraints` | Optional limits: deadlines, output format, size limits, retry policy. |
| `status` | Current task state (see [task-lifecycle.md](task-lifecycle.md)). |
| `result` | The structured output produced on successful completion. |
| `error` | Structured error information on failure. |
| `usage` | Optional execution metadata (see below). |

## Conversation IDs and task IDs

- A **conversation** represents one end-to-end workflow between participants (for example, a user's report request flowing through the Orchestrator to the Researcher and Writer).
- A **task** is a single unit of delegated work within a conversation.
- `conversation_id` stays constant across the workflow; each delegated unit of work carries its own `task_id`. This is what lets asynchronous results be correlated back to the right request even when tasks complete out of order.

## Constraints

Constraints are the delegator's declared limits for a task — for example, a deadline, a required output format, or a maximum result size. Constraint *names and semantics are proposed, not finalized*; the intent is that a receiving agent must be able to either honor a constraint or reject the task explicitly rather than silently ignore it. The reference agent does exactly that (see [http-api.md](http-api.md#submitting-a-task)).

## Results

A **result** is the successful outcome of a task. The proposal is for results to be structured (JSON) rather than free text where possible, so that an Orchestrator can chain results — e.g., feeding Researcher output into a Writer task — without parsing prose. Results travel inside the task payload, so they carry their originating `task_id` and `conversation_id`.

## Errors

Errors are first-class protocol payloads, not just HTTP status codes. A proposed error object includes (*draft*):

- A machine-readable **error code**.
- A human-readable **message**.
- The `task_id` (and `conversation_id`) the error belongs to (carried by the enclosing task payload).
- An optional indicator of whether the error is **retryable** (e.g., transient provider failure vs. malformed request).

Structured errors are what make retry and timeout behavior in [task-lifecycle.md](task-lifecycle.md) actionable. The codes the reference implementation emits are listed in [http-api.md](http-api.md).

## Usage metadata

Agents may report **usage metadata** with results or progress — for example, token counts, model identifiers, or execution duration. This is optional and informational; exact fields are *proposed, not finalized*. It is intended to support observability and cost accounting in later phases.

## What this page deliberately does not define

- Final JSON schemas (drafts exist in `specs/`; finalization is Phase 1 work).
- Exact error-code taxonomies.
- Authentication or authorization semantics (planned for Phase 5).
